# 鸿蒙移植经验与跨平台落点

> 本文回答的是“哪些经验可以迁移到 macOS / Windows / Android，以及现在用到哪一步”，不是发布说明，也不是“所有机型都已支持”的承诺。

## 0. 先统一口径

- **原则层**：下面标注“原则”的条目，可以直接作为四个平台的设计与验收标准。
- **实现层**：标注“已落地”表示当前源码里确有对应实现；标注“缺口”表示只有原则、没有实现；标注“需决策”表示会改变输出统计口径或产品语义，不能直接照搬。
- **结果层**：具体机型能否 0 N/A、纳秒数是否可比，只能实机验证。本文不把“代码可构建”写成“已实测”。

鸿蒙版的价值不是某一组参数，而是把“请求绑核 → 校验真实落点 → 测量期监控 → 失败如实标注”做成了闭环。下面按这个闭环拆开。

## 2. 三条原则为什么可以直接用

### 2.1 真实落点校验

**原则**：绑核调用成功只代表“请求被接受”，不代表线程真的在目标核上跑。

- Windows 的 `SetThreadAffinityMask` 返回非 0 后，必须用 `GetCurrentProcessorNumber`（>64 时用 `GetCurrentProcessorNumberEx`）确认组和编号。
- Android/HarmonyOS 的 `sched_setaffinity` 返回 0 后，必须用 `sched_getaffinity` 读回掩码，再用 `sched_getcpu` 确认落点。
- macOS 没有硬绑核；只能给 QoS/affinity hint。这里不能伪造“已验证”，应明确标成 best-effort。

鸿蒙的额外发现：即便返回 0、掩码也对，线程仍可能在采样窗口内被厂商调度器迁走。所以“测量期监控”不是可选项。

### 2.2 动态拓扑 + 无白名单

**原则**：线程数、SMT 关系、簇、prime 核都应从系统读，不能写死机型表。

- 鸿蒙从 `/sys/devices/system/cpu` 读 `core_id`、`thread_siblings_list`、`physical_package_id`、`cpu_capacity`。
- 读不到就退回逻辑槽位，并明确告知用户“这是逻辑槽位，不是物理核”。
- 绝不出现“某某机型只绑 0–4”这种硬编码。

### 2.3 结果驱动 UI + 连续验证

**原则**：UI 不应按定时器重绘测量状态；原生侧每完成一个结果才通知一次。发布前每个平台至少连续 5 次无 N/A，并记录版本、设备、时间。

鸿蒙版把“每 120 ms 轮询并刷新用时”改成“done 变化才刷新”，这是 Android APK 已有的行为，不是鸿蒙特有发明。

## 3. 明确不能直接照搬的条目

### 3.1 一对只测一次 + 对称填（A5）

鸿蒙版只测上三角一次，再对称填。其他三个版本测所有有序对 `(i,j)` 和 `(j,i)`，再取平均。两者不是“快慢”差异，而是统计量差异：

- 现状：每个方向都测，矩阵值 = 两个方向的平均，能看出方向不对称。
- 鸿蒙：只测一个方向，矩阵对称，用时约少一半。

如果其他版本要采用，必须先确定输出契约：是否保留方向信息、CSV 是否仍满足旧脚本、数值如何与历史结果比较。**不要偷偷换掉。**

### 3.2 短窗口多轮（A6）

鸿蒙的 500 次/轮、800 轮/方向、至少 64 轮，是为了在厂商调度器频繁迁移的环境里“短窗口 + 多轮取最小值”。Windows/macOS 的固定 100 万次 × 10 run 在稳定环境里更简单，直接换成短窗口会改变测量分布和总用时。需要逐平台 A/B，不是复制粘贴。

### 3.3 Android/macOS 物理核 ID（D3）

- Android 读 sysfs 可能被 SELinux 拦截，必须 best-effort，读不到退回逻辑槽位。
- macOS 没有公开的“物理核 ID → 逻辑 CPU”稳定映射；`hw.perflevel` 只给性能档数量，不是逐核 ID。
- 如果只改标签、不改矩阵维度，风险较低；如果改成“只测物理核”，矩阵会从 9×9 变成 6×6，结果不可比。这是产品决策。

### 3.4 macOS 的 N/A（D4）

macOS 不能硬绑核。把 macOS 全部标 N/A 会让工具失去“尽力而为测量”的用途；正确做法是三态：

- `verified`：真正验证到目标核（macOS 没有）；
- `best-effort`：QoS/hint 已设置，但落点未验证；
- `N/A`：连 hint 都无法设置，或测量期明显漂移。

当前 macOS 代码只有“成功”一态，这是缺口，但不能用“全 N/A”来假装解决。

## 4. 建议的落地顺序

1. **Windows processor group（D2）**：代码缺口最明确，影响 >64 逻辑处理器；<=64 路径应保持不变。可在本机 32 逻辑处理器上编译回归，>64 需另找机器或虚拟机验证。
2. **Android sysfs 拓扑（D3，只读展示）**：先只改 `--list` 和标签，矩阵维度不动；读不到就退回逻辑槽位。需要真机验证 SELinux 行为。
3. **macOS 三态标注（D4）**：先改输出语义和文档，不改数值；需要确认 CSV 是否增加 placement 列。
4. **A5/A6**：只做可选开关或新版本，不默认替换；用同一台机器做 A/B，比较均值、分位数和总用时。
5. **E1/E4/F4**：补每个平台的连续运行记录和失败日志；这是验证工作，不是打包工作。

## 5. 验收标准（可直接拿去用）

- **Windows >64**：`--list` 的逻辑 CPU 数等于所有 group 的 `GetActiveProcessorCount` 之和；每个 worker 的 `GetCurrentProcessorNumberEx` 组号和编号都等于请求值；<=64 时矩阵与旧版差异在噪声内。
- **Android 拓扑**：`--list` 能显示物理核 ID/SMT（若 sysfs 可读）；读不到时明确打印 fallback；矩阵维度不变。
- **macOS 三态**：输出/CSV 能区分 best-effort 与 verified；不出现“已验证”但实际未验证的字样。
- **回归**：同一台机器连续 5 次运行，N/A 数与基线一致；矩阵关键格（同核/跨核）在历史噪声范围内。
- **文档**：README、使用手册、Release 说明三处口径一致；不把“代码可构建”写成“所有机型已实测”。

## 6. 这份清单怎么“使用”

- 它是**审计表**：每改一个平台，先找到对应行，写清楚“已落地/缺口/需决策”，再动代码。
- 它是**验收表**：第 5 节每一条都能变成测试项，不靠“看起来没问题”。
- 它是**边界表**：对外描述时，只承诺已经实机验证的部分；原则层可以直接说“适用”，实现层和结果层必须限定条件。

最后一句：**发布包不是推广，源码与验收标准才是。**
