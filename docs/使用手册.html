CoherencyLatency macOS 使用手册

版本： 1.1.0（对应 MicroBenchX 1.0.5） 适用平台： Intel（x86_64）Mac：macOS 10.7 Lion 或更高；Apple Silicon（arm64）Mac：macOS 11.0 或更高。主程序为 Universal 2 单文件。

重要限制：macOS 不提供硬性 CPU 绑定。本工具不能保证测量“指定 core i ↔ core j”的核间延迟；矩阵中的 i/j 只是逻辑槽位，不是物理核心编号，也不保证线程落在指定的 P 核或 E 核上。若要测量严格的核心对延迟，请使用原版 Windows 程序，或 Linux 上支持 taskset/sched_setaffinity 的环境。

1. 文件夹内容

CoherencyLatency-macOS-Release/
└── CoherencyLatency      主程序（Universal 2：x86_64 + arm64）

主程序是自包含的 Universal 2 可执行文件（Intel x86_64 + Apple Silicon arm64），只依赖 macOS 自带的 /usr/lib/libSystem.B.dylib，不需要安装 Homebrew、CMake 或其他运行库。

2. 首次运行

2.1 放到本地目录

建议先把整个文件夹复制到“应用程序”或“下载”之外的位置，例如：

~/Applications/CoherencyLatency-macOS-Release

不要直接在 ZIP 压缩包里运行。

2.2 解除权限和隔离

打开“终端”，进入文件夹：

cd ~/Applications/CoherencyLatency-macOS-Release
chmod +x CoherencyLatency
xattr -dr com.apple.quarantine .

如果 macOS 仍提示“无法打开，因为无法验证开发者”：

  1. 在 Finder 中右键点击 CoherencyLatency，选择“打开”；
  2. 或到“系统设置 → 隐私与安全性”中点击“仍要打开”；
  3. 仍不行时执行：
codesign --force --deep --sign - CoherencyLatency

2.3 先检查程序

./CoherencyLatency --list

应看到 CoherencyLatency 1.1.0 和 CPU 信息。--list 不会运行测试。

3. 启动方式

单文件版直接从「终端」运行即可；下文的命令行示例适用于所有测试方式。

标准测试在核心数较多的 Mac 上会运行很久。第一次使用建议先运行下面的“快速测试”。

4. 命令行使用

4.1 查看 CPU

./CoherencyLatency --list

4.2 快速测试

./CoherencyLatency --yes --cpus 2 --iterations 100000 --runs 3

只使用 2 个逻辑槽位，适合先确认程序能运行和观察大致延迟。

4.3 标准测试

./CoherencyLatency --yes

默认参数是每个线程 1,000,000 次操作、每个核心对 10 runs。核心数越多，耗时增长很快；可以随时按 Ctrl+C 停止。

4.4 owned 模式

./CoherencyLatency --yes --mode owned --cpus 2 --iterations 100000 --runs 3

bounce 模式让两个线程竞争同一条 cache line；owned 模式让两个线程各自写自己的 cache line，再读取对方的 line。

4.5 指定 CSV 路径

./CoherencyLatency --yes --csv result.csv

不指定时，默认写入当前目录的：

core_latencies_YYYYMMDD_HHMMSS.csv

4.6 兼容原版位置参数

./CoherencyLatency 1000000 bounce
./CoherencyLatency 1000000 owned

5. 输出格式

5.1 终端显示

终端输出是逗号分隔的矩阵，对角线为 x：

x,123.456789
123.456789,x

5.2 CSV 文件

CSV 与原版 v1.0.5 一致：

  • 文件名：core_latencies_YYYYMMDD_HHMMSS.csv
  • 分隔符：分号 ;
  • 第一行：;Core 0;Core 1...
  • 每一行：Core i;值;值...
  • 对角线：x
  • 数值按原版 defaultfloat 精度 6 输出

原版输出的是 CSV，不是 XLSX。CSV 可以直接用 Excel 或 Numbers 打开，也可以在 Excel 中另存为 .xlsx；程序本身不生成 xlsx。

关于 N/A：同一份源码构建的 Windows 版会在绑核失败时把对应格子写成 N/A（详见 Windows 使用说明第 5 节）。macOS 没有硬绑定能力，因此 macOS 版不会出现 N/A，格子里的数字只代表“两个线程之间的实测延迟”，不代表已经锁定到某个物理核心。

7. 结果解读与限制

  • 本移植测量的是两个线程之间的 cache-line 一致性延迟样本，不是严格的核心对拓扑矩阵。
  • 矩阵的行列号只是逻辑槽位，不能解释为“物理 Core 0 到 Core 1”的延迟。
  • macOS 调度器可能迁移线程，尤其是 P 核与 E 核之间；同一台 Mac 上不同次运行也可能有差异。
  • 不要直接把 macOS 的数值和 Windows 原版数值比较；平台和调度模型不同。
  • 想获得相对稳定的对比：连接电源、关闭其他应用、避免热降频，并固定 --cpus 和 --perf-only 的组合。
  • macOS 版不会输出 N/A：系统没有硬绑定，程序无法验证线程落在哪个核心，所以只如实给出实测值。Windows 版会在绑核失败时写 N/A，两边的输出不能混用同一套判读规则。

8. 性能与内存

本移植在保持命令行参数、测试次数、统计方式和输出格式完全不变的前提下，降低了运行开销和内存占用：

  • 线程只创建一次：原版对每个核心对、每一次 run 都 CreateThread 两个线程，跑完就 CloseHandle；移植版对每个核心对只创建两个线程，用逐轮的启动闸门复用它们跑完所有 run。线程创建和销毁的开销不再混进测量，run 越多收益越明显。
  • 计时改成整数高精度时钟：Windows 用 QueryPerformanceCounter（频率只查一次），macOS 用 mach_absolute_time，换算全程整数运算；不再使用毫秒精度的 ftime，短测试的时间分辨率不再受 1 ms 限制。
  • 矩阵内存由 O(n² × runs) 降到 O(n²)：原版会把每个核心对、每次 run 的原始样本全部存进内存，最后再求最小值；现在每得到一个样本就与当前最小值比较并保留较小者，只保留最终的 n × n 最小延迟矩阵。以 32 个逻辑槽位、50 次 run 为例，样本缓冲从 200 KB 降为固定的 4 KB（32 × 32 × 4 字节），并且不再随 --runs 增长。
  • 没有堆分配：采样用的 cache-line 单元改为栈上对象，bounce 和 owned 两种模式都不再使用 new/make_unique，整个程序没有显式的动态内存分配。
  • 进度条更跟手：每完成一个核心对就重绘一次，不再像原版那样跑完一整行才刷新（核心多时原版会长时间停在 [>] 0 %）。一次重绘只是一行定长输出，开销远小于单个核心对的测量时间。
  • 输出完全不变：CSV 的列顺序、对角线 x、6 位有效数字精度与原版一致；调大 --runs 只会让采样更久，内存占用不再增加。

8.1 实测对比

测试机：Windows 11，AMD 32 逻辑处理器，x64 原生程序，--yes --no-progress，每个用例跑 3 次取中位数。

--cpus 8 --iterations 1000 --runs 10139 ms54 ms−61%
--cpus 16 --iterations 1000 --runs 10401 ms180 ms−55%
--cpus 32 --iterations 1000 --runs 102914 ms1612 ms−45%
--cpus 8 --iterations 1000 --runs 10 --mode owned148 ms70 ms−53%

--cpus 4 --iterations 200000 --runs 5603 ms591 ms−2%

规律很直接：测试越短，线程创建/销毁的固定开销占比越大，提速越明显；--iterations 上到几十万以后，时间几乎全部花在测量本身，两边就基本持平——那部分耗时是测量必需的，不是额外开销。

8.2 测量数值与原版的对齐情况

优化只降低整轮耗时和内存占用，不会改变测得的每操作延迟：测量窗口同样是"两个工作线程就绪后开始、跑完结束"，不包含线程创建，与原版 ResumeThread 前后取时间的做法一致。

在同机交叉实测中（4 槽位、每 run 100 万次迭代、10 次 run，两个程序交替运行），移植版与原版源码重编译程序的矩阵数值差距在 0.1–2.4 ns 之间，且随会话波动——线程在处理器核心组之间迁移本身就会带来 ±2–3 ns 的漂移，噪声占主导，两边的单次 run 都能观察到 17→29 ns 的漂移带。

数值上的少量差异来自两处刻意的修正，而不是开销优化：

  • 统计量：移植版取全部 run 的最小值；原版源码在最小值判断处多了一个分号，实际输出的是最后一次 run 的结果。原版输出的波动因此更大。
  • 计时精度：移植版用纳秒级高精度时钟（Windows QueryPerformanceCounter、macOS mach_absolute_time）；原版用毫秒级的 ftime，短测试的时间分辨率受限。

结论：与原版相比，输出只存在个位数纳秒级的抖动，属于测量噪声而非系统偏差；如果与原版的输出逐格对比，应以几纳秒的容差来比较。

说明：减小 --iterations 或 --runs 会直接缩短运行时间，那属于测量本身的耗时，不是额外开销。程序常驻内存只有几 MB，长时间测试也不会持续增长。

9. 常见问题

提示“Permission denied”

chmod +x CoherencyLatency

提示“cannot be opened because the developer cannot be verified”

按 2.2 节执行 xattr，或在 Finder 中右键选择“打开”。

提示“bad CPU type in executable”

说明当前系统版本低于本程序的最低要求（Intel Mac 需 macOS 10.7+，Apple Silicon Mac 需 macOS 11.0+），或者文件下载不完整/架构识别异常。本程序是 Universal 2 单文件，同时包含 x86_64 和 arm64。

程序被系统杀掉

尝试重新签名：

codesign --force --deep --sign - CoherencyLatency

测试运行太久

按 Ctrl+C 停止，改用：

./CoherencyLatency --yes --cpus 2 --iterations 100000 --runs 3

想确认文件没有损坏

shasum -a 256 CoherencyLatency

把输出与 SHA256SUMS 中的值比较。

10. 卸载

直接删除整个文件夹即可。程序不会写入系统目录，也不会安装后台服务；CSV 文件默认写在当前运行目录。
